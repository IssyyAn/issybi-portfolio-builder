# Planning Framework

For a full brief, cover the sections below at a depth appropriate to the request. For a focused revision or review, return only relevant sections. Apply the evidence contract; do not repeat answered intake questions.

## Purpose and inspection

State the working title, purpose, starting artifacts, learner goal, tools, time box, and known constraints. Include the compact inspection record from evidence-contract.md. A conditional plan can proceed from structural evidence with unverified assumptions marked; a topic-only request starts with data acquisition or an explicitly provisional concept.

## Stakeholder and decision

Use a supplied suitable route, or recommend a specific stakeholder and one decision they can realistically act on. Explain why the data fits. Offer alternatives only where their trade-offs materially change the project. Narrow an unsupported decision or overly broad role; do not invent internal organisational objectives or a commission.

## Feasibility and connected questions

Choose the smallest useful set of questions needed for that decision. Map each to source fields and grain, rationale, Supported / Derivable / Not supported feasibility, and calculation or transformation where needed. Mark schema- or sample-based feasibility as provisional. Keep Not supported questions in boundaries with the missing evidence identified.

## Measures or evaluation criteria

Define only measures needed by the questions. Include name, meaning, unit, formula logic, denominator where applicable, required fields, filters/time basis, aggregation, and interpretation risks. Document joins and missing-value treatment when they affect validity. Use tests, quality criteria, or model evaluation instead of KPI language when appropriate. Write executable formulas or queries when requested or in the build stage; planning logic alone must not be presented as executed analysis.

## Build, validation, and presentation

Outline the minimum preparation, modelling, analysis, validation, and presentation work. Distinguish completed work from proposed work. Pick the format from the decision, and map each visual to a question. For requested dashboard mockups, follow dashboard-mockups.md and produce the artifact plus implementation notes. Avoid pages, measures, and technologies added only to fill a template.

## Portfolio evidence and learning

Specify what a reviewer can inspect without the original working file: sources/licensing, brief, transformations, key modelling choices, code or measures, validation results, suitable screenshots or output extracts, findings after execution, and limitations. Separate AI assistance and learner decisions; never invent realised impact.

When teaching, include a relevant judgement checkpoint that exercises a choice made in this project. For example, ask which denominator best serves the decision and give the consequences of each option. Respect execution-only or no-quiz requests.

## Boundaries and next action

State unknowns, out-of-scope questions, missing evidence, pending validation, and the next useful action. Do not present a provisional plan or illustrative design as a validated analytical result.
